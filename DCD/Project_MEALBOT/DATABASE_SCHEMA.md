# MealBot Database Schema Proposal

> Status: **design only**. This file does not connect to, create, or migrate a
> database. It is the proposed PostgreSQL model for the D1–D3 MVP and its CNT
> integration boundary.

## Bootstrap Artifact

The reviewed design is implemented as an idempotent SQL skeleton at
[`database/mealbot_schema.sql`](../../database/mealbot_schema.sql). After a
PostgreSQL database exists, run it through:

```bash
MEALBOT_DATABASE_URL='postgresql://user:password@host:5432/mealbot' \
  python scripts/create_postgres_schema.py
```

This creates tables only. It does not convert the running in-memory domain
repositories to PostgreSQL yet.

## CNT Ownership Boundary

```text
n8n ── schedule, retry, API orchestration ──┐
Telegram ── human interaction ──────────────┼──> MealBot API
                                             │
                                             ▼
                                  MealBot: D1, D2, D3 rules
                                             │
                                             ▼
                                  PostgreSQL: business truth
```

| Concern | Owner | Must not own |
|---|---|---|
| Home, preferences, polls, votes, winner, plan | MealBot code + PostgreSQL | n8n or Telegram |
| When to open/close a poll; retries; calling APIs | n8n | vote rules or winner selection |
| Displaying a poll and receiving a human action | Telegram (transport) | business state |

**Important:** n8n must call MealBot APIs; it must not write D1, D2, or D3
business tables directly. PostgreSQL is MealBot's persistent memory, not n8n's
working database.

## Data Flow

```text
Home ──< Resident ──< MealPreferenceVersion ──< MealPreferenceItem
                 │
                 └──< ResidentTransportIdentity
  │
  ├──< Cook
  │
  ├──< DailyMealPoll ──< PollOption ──< MealVote
  │         │
  │         └── MealSummary ──< MealPlan
  │
  └──< TransportEndpoint ──< TransportPollBinding >── DailyMealPoll
```

1. D1 records a Home, its Residents, and its current Cook.
2. D2 appends a MealPreference version and marks the previous version as no
   longer current. Each version contains exactly five meal items.
3. D3 creates one poll for a Home and meal date, with three poll options.
4. Residents cast votes. The database proves that the resident and selected
   option both belong to that poll's Home.
5. Closing a poll creates one summary and one final plan.
6. n8n creates the external Telegram poll and records its external identity in
   `transport_poll_bindings`; incoming transport events are then mapped back
   to the correct MealBot poll.

## Conventions

- Every primary key is a UUID generated by PostgreSQL.
- Timestamps use `timestamptz` in UTC.
- Phone numbers and meal names are `text`; existing application normalization
  still owns their format.
- PostgreSQL `CHECK` constraints should enforce the status and preference
  values below. Prefer checks over PostgreSQL enums for this evolving MVP.
- Composite keys shown below are deliberate: they let PostgreSQL reject
  cross-home and cross-poll relationships that are individually valid but
  business-wise impossible.

## D1 — Home Management

### `homes`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `name` | text | required |
| `status` | text | required; check `Active`, `Archived` |
| `created_at` | timestamptz | required |

No unique-name constraint is proposed; the current business rules allow it.

### `residents`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; foreign key to `homes.id` |
| `name` | text | required |
| `phone` | text | required |
| `status` | text | required; check `Active`, `Archived` |
| `onboarded_at` | timestamptz | required |

Constraints: `unique (home_id, phone)` and `unique (home_id, id)`. The second
one is intentionally addressable by composite foreign keys from D3.

### `cooks`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; foreign key to `homes.id`; unique |
| `name` | text | required |
| `phone` | text | required |
| `status` | text | required; check `Active`, `Archived` |
| `assigned_at` | timestamptz | required |

Constraints: `unique (home_id)` and `unique (home_id, id)`. This represents
the current cook only; cook-assignment history remains out of scope.

## D2 — Meal Planning

### `meal_preferences`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `resident_id` | uuid | required; foreign key to `residents.id` |
| `version` | integer | required; starts at 1 per resident |
| `protein_preference` | text | required; allowed D2 protein values |
| `spice_preference` | text | required; allowed D2 spice values |
| `is_current` | boolean | required |
| `created_at` | timestamptz | required |
| `superseded_at` | timestamptz | nullable; set when replaced |

Constraints: `unique (resident_id, version)` and a partial unique index on
`resident_id where is_current`. This preserves the current runtime behaviour:
preference history exists, but D3 selects exactly the current/latest version.

### `meal_preference_items`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `meal_preference_id` | uuid | required; foreign key to `meal_preferences.id` |
| `meal_name` | text | required; normalized lowercase |
| `position` | smallint | required; check 1 through 5 |

Constraints: `unique (meal_preference_id, meal_name)` and `unique
(meal_preference_id, position)`. D2's save workflow must continue to require
exactly five items before marking a version current.

## D3 — Daily Meal Coordination

### `daily_meal_polls`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; foreign key to `homes.id` |
| `meal_date` | date | required |
| `status` | text | required; check `Draft`, `Open`, `Closed` |
| `opened_at` | timestamptz | nullable until opened |
| `closed_at` | timestamptz | nullable until closed |

Constraints: `unique (home_id, meal_date)` and `unique (home_id, id)`.
`opened_at` and `closed_at` record truth; n8n, not this table, owns the
two-hour scheduling decision.

### `poll_options`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `poll_id` | uuid | required; foreign key to `daily_meal_polls.id` |
| `meal_name` | text | required; normalized lowercase |
| `rank` | smallint | required; check 1 through 3 |

Constraints: `unique (poll_id, meal_name)`, `unique (poll_id, rank)`, and
`unique (poll_id, id)`. D3 creates exactly three options.

### `meal_votes`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; integrity column |
| `poll_id` | uuid | required; integrity column |
| `poll_option_id` | uuid | required; integrity column |
| `resident_id` | uuid | required; integrity column |
| `submitted_at` | timestamptz | required |

Constraints:

- `unique (poll_id, resident_id)` — one resident vote per poll.
- `(home_id, poll_id)` references `daily_meal_polls (home_id, id)`.
- `(home_id, resident_id)` references `residents (home_id, id)`.
- `(poll_id, poll_option_id)` references `poll_options (poll_id, id)`.

The redundant IDs are intentional. Together they prevent a vote from using an
option from another poll or a resident from another Home.

### `meal_summaries`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; integrity column |
| `poll_id` | uuid | required; foreign key relationship |
| `winning_poll_option_id` | uuid | required; foreign key relationship |
| `total_votes` | integer | required; check at least 1 |
| `created_at` | timestamptz | required |

Constraints: `unique (poll_id)`, `unique (home_id, id)`,
`(home_id, poll_id)` references `daily_meal_polls (home_id, id)`, and
`(poll_id, winning_poll_option_id)` references `poll_options (poll_id, id)`.
Vote counts remain derived from `meal_votes`; `total_votes` is the immutable
close-time snapshot.

### `meal_plans`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; integrity column |
| `meal_summary_id` | uuid | required; foreign key relationship |
| `cook_id` | uuid | required; foreign key relationship |
| `meal_date` | date | required |
| `meal_name` | text | required; immutable winning-meal snapshot |
| `created_at` | timestamptz | required |

Constraints: `unique (meal_summary_id)`, `unique (home_id, meal_date)`,
`(home_id, meal_summary_id)` references `meal_summaries (home_id, id)`, and
`(home_id, cook_id)` references `cooks (home_id, id)`.

`vote_count` is deliberately absent. It answers "what happened?" and belongs
to `meal_summaries`; `meal_plans` answers only "what must be prepared?".

## CNT Integration Boundary (not D4 business logic)

These tables record durable external identity. They do not move business rules
into n8n, Telegram, or a new domain.

### `transport_endpoints`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `home_id` | uuid | required; foreign key to `homes.id` |
| `provider` | text | required; initially `telegram` |
| `purpose` | text | required; initially `resident_poll` or `cook_notification` |
| `external_destination_id` | text | required; e.g. Telegram chat ID |
| `status` | text | required; check `Active`, `Inactive` |
| `created_at` | timestamptz | required |

Constraint: `unique (home_id, provider, purpose)`. This says where a
particular Home's resident poll or cook notification is delivered.

### `resident_transport_identities`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `resident_id` | uuid | required; foreign key to `residents.id` |
| `provider` | text | required; initially `telegram` |
| `external_user_id` | text | required; provider's stable user identity |
| `status` | text | required; check `Active`, `Inactive` |
| `linked_at` | timestamptz | required |

Constraints: `unique (resident_id, provider)` and `unique (provider,
external_user_id)`. A Telegram event identifies a Telegram user, not a
resident phone number. This binding lets a MealBot API resolve that external
identity to exactly one eligible resident before it submits a vote.

### `transport_poll_bindings`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `daily_meal_poll_id` | uuid | required; foreign key to `daily_meal_polls.id` |
| `transport_endpoint_id` | uuid | required; foreign key to `transport_endpoints.id` |
| `provider_poll_id` | text | required; external poll identity |
| `provider_message_id` | text | nullable; external message identity |
| `created_at` | timestamptz | required |
| `closed_at` | timestamptz | nullable |

Constraints: `unique (daily_meal_poll_id, transport_endpoint_id)` and `unique
(transport_endpoint_id, provider_poll_id)`. n8n uses this durable mapping to
turn an incoming Telegram event into a MealBot vote for the correct poll.

## API Reliability Requirements Before n8n

These are API and workflow requirements, not additional business domains:

- `POST /daily-meal-polls` and close operations need idempotency keys so n8n
  retries return the existing result instead of failing or duplicating work.
- MealBot needs a capability to list Homes eligible for a scheduled poll; n8n
  should not query business tables directly.
- After Telegram creates a poll, n8n must call a MealBot API that records the
  `transport_poll_bindings` row.
- Telegram vote events must identify the resident through
  `resident_transport_identities`; n8n must not invent or trust a phone number
  supplied by the transport event.
- A failed Telegram action must be retryable without changing the winning meal
  or duplicating the external poll/message.

## Explicitly Out of Scope

- Direct n8n writes to MealBot business tables.
- User accounts, authentication, and authorization.
- Telegram credentials, n8n execution logs, and transport-provider secrets.
- Notification delivery/retry history beyond the poll binding.
- A global meal catalogue, nutrition data, AI recommendation data, and cook
  assignment history.

Add each only when its owner and business rule are defined.
